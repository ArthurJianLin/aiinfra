一、结论速览

prefill 是"一发大脉冲"，decode 是"等距小节拍"。1184 token 的 prompt 前向只需 1 个引擎步（GPU 19.1 ms、529 个大内核，GEMM/FlashAttention 主导）；随后每个生成 token 是一个约 3.6 ms 的小步（278 个 µs 级小内核，GEMV/splitKV 主导）。两阶段在时间轴上的形态截然不同——这正是 continuous batching、chunked prefill 与 PD 分离要解决的问题。

二、目标与方法

对应《02-主线学习路线图》行动清单第 2 项：完成一次推理 profile，看清 prefill 与 decode 两阶段在时间轴上的形态，并写 300 字观察。

实验设计（同一进程三次 generate，NVTX / record_function 相位标记）：

  • 测量甲（prefill_only）：新 prompt（≈1184 tokens）+ max_tokens=1 → 得到孤立 prefill；
  • 测量乙（prefill_decode）：新 prompt + max_tokens=129 → prefill + 128 步 decode（ignore_eos=True 保证步数确定）；
  • 两组相减 → 每步 decode 时延：(499.83 − 24.61) / 128 ≈ 3.71 ms/token ≈ 269 tok/s（单流）。

五、中间遇到的问题与解决

  1. 问题 1 · matplotlib 升级连坐破坏 vllm 依赖

    现象：pip 安装最新 matplotlib 3.11.2 时连带把 numpy 升到 2.5.4，与 numba 0.60（要求 numpy<2.1）和 vllm 0.7.3 栈冲突。
    解决：改用 pip install matplotlib==3.9.4 numpy==1.26.4，依赖恢复干净。教训：在受版本锁定的推理栈里补工具包必须显式 pin。

  2. 问题 2 · nsys 三条常规途径全被堵

    现象：机器未装 nsys；pip（清华镜像无此包）；无免密 sudo（apt 装 .deb 不可行）。
    解决：官网 get-started 页找到 2026.5.1 Linux .run 直链（446MB，国内 CDN 可达），--target 解包到家目录运行，无需 root。

  3. 问题 3 · makeself 解包幽灵报错"未知选项 -title"

    现象：执行 .run 反复报"无法处理参数：未知选项 -title"，但 --list/--check 又正常。
    根因：两个叠加因素——① 本机 /bin/sh 是 dash，makeself 的参数解析踩坑；② 这台是桌面机（DISPLAY=:0），makeself 检测到非 TTY 便会尝试 exec gnome-terminal -title ... 弹窗运行，而新版 gnome-terminal 已移除 -title 参数。
    解决：bash 执行 + 加 --nox11 参数，解包成功。教训：桌面环境下跑安装器，先想到 --nox11。

  4. 问题 4（核心）· nsys 采集到 0 个 CUDA 事件

    现象：正式采集的 .nsys-rep 导出 sqlite 后只有 3 条 NVTX 事件，没有任何 CUDA API / kernel 表；nsys stats 报 "does not contain CUDA kernel data"。最小复现：纯 torch.matmul 也是 0 内核。
    根因（DIAGNOSTIC_EVENT 86 条诊断日志实锤）：
    Loaded CUPTI library: libcupti.so.12.9
    EnableOptionalDriverCallback(CUPTI_DRIVER_TRACE_CBID_cuGreenCtxDestroy) → CUPTI_ERROR_INVALID_PARAMETER
    CUDA injection initialization failed
    nsys 2026.5 自带 CUPTI 12.9，初始化时要启用 CUDA 12.4+ 才有的 Green Context 驱动回调；本机 GPU 为 A10-24Q（vGPU 规格）+ 驱动 535（CUDA 12.2 上限，锁定不可升级），驱动不认识该回调 → CUDA 注入整体初始化失败（静默降级，仅警告级别诊断）。
    解决：换用 torch 2.5.1 自带的 CUPTI 12.1（nvidia-cuda-cupti-cu12==12.1.105，与 CUDA 12.2 驱动完全匹配）→ torch profiler 成功采到内核级数据。教训：profiler 的 CUPTI 版本必须 ≤ 驱动 CUDA 版本，CUPTI 过新会把整条 CUDA 采集搞挂。

  5. 问题 5 · vLLM hook 踩版本 API 坑

    现象：hook Scheduler.schedule() 后取返回值接连报错（先是 tuple、后是 list 没有 num_prefill_groups）。
    根因：vllm 0.7.3 的 schedule() 返回三元组 (seq_group_metadata_list, SchedulerOutputs, allow_async)，SchedulerOutputs 在 下标 1。
    解决：hook 里取 out[1]，分类用 num_prefill_groups > 0 判 prefill 步。

  6. 问题 6 · nsys CPU 采样被系统安全策略禁用

    现象：nsys 启动即警告 CPU IP/backtrace 采样、上下文切换跟踪不可用（nsys status --environment：perf_event_paranoid=4，perf_event_open 被拒）。
    处理：本实验只需 GPU 时间轴，CPU 采样缺失不影响结论；如需 CPU 侧剖析需管理员下调 paranoid 等级（本机不可行，记录在案）。

六、结果详解

6.1 全景时间轴：两阶段形态一目了然

两张图（引擎步视角与内核视角）形态完全对应：一个高耸的 prefill 脉冲之后，跟随一串低矮、等间距、周期约 3.6 ms 的 decode 齿。

6.2 prefill 放大：一次前向，529 个大内核

prefill 阶段 Top 内核（与 24 层 Transformer 结构一一对应）
内核次数累计结构性解读
cutlass bf16 GEMM 256x128488.14 ms24 层 × 2（QKV/O/lm 投影型大 GEMM）
cutlass bf16 GEMM 128x256242.82 ms24 层 × 1（gate/up 投影）
vllm act_and_mul (silu)481.84 ms激活函数

gemv2T / gemvx 等72+21.80 mslm_head 与小投影

解读：prefill 的耗时几乎全部坐在 GEMM 上（约 11 ms / 19.9 ms busy），大矩阵乘让 SM 吃满，这是"算力受限"段的形态；内核数目与 24 层结构呈整倍数关系，可以用层数直接核对采集质量。

6.3 decode 放大：128 步 × 278 个 µs 级小内核

decode 每步内核构成（乘以 128 步的总量在括号内）
内核（decode 主力）每步累计解读
gemvx / gemv2T（batch=1 GEMV）72+1171.9 msbatch=1 时 GEMM 退化成 GEMV，算力大量闲置
cutlass wmma 16x16 小 GEMM24107.6 ms24 层 × 1

解读：decode 每步固定发射约 278 个内核——层数的整倍数组合（24/48/72），形态是"很多小 kernel 各干一点活"。这正是 CUDA Graph 的用武之地：把每步的固定 launch 序列固化成整图，一次 cudaGraphLaunch 回放，消除 CPU 发射延迟。

6.4 decode 步解剖：忙时 ≈ 间隔

关键观察：decode 的 GPU 忙时与步间隔几乎相等（99.6% 忙占比）——不存在"等 CPU 发射"的空泡，瓶颈在每步 3.6 ms 的 GPU 工作本身（GEMV + 每步数百次小内核的访存）。要提速单条 decode，方向是减小每步工作（量化、更快的 attention kernel）或靠 continuous batching 把多条请求拼进同一步提高硬件利用率，而不是压缩调度间隙。

七、300 字观察（对应 02 文档验收项）

在时间轴上，vLLM 的一轮推理呈现两种截然相反的形态。prefill 是一发大脉冲：1184 个 token 打包成一次前向，19.1 ms 内连续发射 529 个大内核，GEMM 单核 20–300 μs、累计占 busy 的一半以上，GPU 忙达 87%，接近算力受限。decode 则是等距小节拍：每 3.6 ms 一步，每步固定 278 个 µs 级小内核（GEMV、splitKV、rotary），由 CUDA Graph 整图回放驱动；忙时与间隔几乎相等（99.6%），说明延迟吃在每步的 GPU 工作本身——batch=1 时权重矩阵只能按 GEMV 方式一遍遍扫，算力被访存稀释。两阶段的形态差正是调度层设计的出发点：continuous batching 把小步攒批、chunked prefill 把大脉冲切片、PD 分离干脆让两种形态上不同的机器。另：本机为 vGPU 且 CUPTI 版本受限，decode 绝对值偏保守，跨机对比应注明环境。
